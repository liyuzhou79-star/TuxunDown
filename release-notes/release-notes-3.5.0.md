# TuxunDown v3.5.0

3.5.0 做两件看得见的新东西和一轮审计：任务详情里能看分片进度图和每条连接的实时速度了；第 21 轮审计查的是预约下载与每天定时的可靠性——到点开始到底靠什么、省电模式和重启会不会把它弄丢——并给它加了一个不需要新权限的系统闹钟兜底。

## 新功能

- **分片进度图**（任务卡片 → 详细信息）：一张小格子图，一格代表一块分片：绿 = 已下完，亮绿 = 正在下，灰 = 还没下。分片太多时（超过 72 块）会自动聚合，每格代表连续的好几块，半绿表示这一格里下了一部分，图下方的说明会写清每格代表几块。流媒体（m3u8）任务按「已合并的段」画——合并是严格按顺序的，绿色就是真正拼好的部分，亮绿是正在处理的那一段；后面的段可能已经在同时下载，但没合并就不算数，图上不会冒充。单线程任务（服务器不支持分片、或 FTP）没有分片图，会在原地写明原因，不留空白让人猜。
- **连接明细**（任务卡片 → 详细信息，下载中才有）：每条连接一行，写清它在下第几块分片、当前速度、这条连接已下多少 / 这一块共多大，每秒刷新。哪条连接在拖后腿、哪条已经停住，一眼就能看出来。数据来源是下载引擎本来就有的每秒采样：每条连接这一秒走了多少字节，采样时顺手记下来发布，没有为这个功能新开任何轮询或定时器。任务暂停或下完，明细自动消失，不会留着过期数字冒充实时。流媒体任务的并行连接没有逐条记录，所以不显示连接明细（它的分片图就是进度视图），这一点不装。

## 审计（第 21 轮：Doze 与定时可靠性）

把「预约下载 / 每天定时到点开始」这件事从代码层核了一遍：

- **现在的机制（核清）**：到点开始靠的是下载服务的前台进程活着等——队列里只剩下未来的预约任务时，服务不退出，挂着「预约下载待机」的通知，每 2–30 秒醒一次看时间到没到。没有任何闹钟参与。
- **Doze / 省电模式（核过）**：服务活着的时候，App 属于前台应用，Doze 不冻结它的线程和网络；而且这个等待是活线程在睡，不是闹钟，闹钟在 Doze 里被推迟那套规则管不到它。所以息屏放一夜、服务没被杀的话，预约是准时的。
- **真正的风险（核清）**：进程死了就什么都没了——从最近任务划掉、被 Flyme 这类系统冻结杀掉、强行停止，都会让服务消失；START_STICKY 的系统重启不可靠，这类 ROM 上划掉基本等于不再拉起。手机在预约时间之前重启也一样：开机接收器只在「开机后自动恢复」开关（默认关）打开时才踢服务。好消息是任务永远不会丢：服务下次起来（打开 App、或任何一次下载启动服务）会立刻把已到点的预约补上——只是晚开始。
- **改进：加了一个兜底闹钟**。现在队列里有未来的预约时，会在最早的那个时间上设一个系统闹钟；闹钟响时如果真有任务到点，就把服务叫起来开下，顺手把闹钟改设到下一个预约。开机时也会重新设（闹钟不跨重启保留）。关键取舍写明：
  - 用的是**不精确闹钟**（setAndAllowWhileIdle），不需要任何新权限；精确闹钟要 SCHEDULE_EXACT_ALARM 这个系统权限，本版明确不用。所以兜底可能晚几分钟，深度省电时系统还可能再往后推——它是兜底，不是秒表；
  - 安卓 12 以后，后台拉起前台服务会被系统拦，除非 App 在电池白名单里。所以闹钟 + 白名单才是最稳的组合；没进白名单又被拦下时，闹钟不报错、不重试轰炸，任务等下次打开 App 时补上，和以前一样；
  - 服务本来就活着的时候，闹钟响了也只是多叫一次，队列该怎么走还怎么走，无副作用。
- **文案同步**：设置 → 后台运行里补了一段预约与保活的关系说明；帮助中心新增「预约下载、每天定时，准时吗？」，把机制、可能晚的原因和怎么设置最稳都讲清了，不把话说满。

## 说明

- 升级方式不变：正式签名与之前一致，直接覆盖安装即可，不用卸载，任务记录都保留。
- 没有新增任何权限（兜底闹钟用的是免权限的不精确闹钟；清单里只多了一个接收它广播的内部组件，外部应用调不到）；没有新增任何第三方依赖。
- 安装包体积：以正式发布包实测为准（验收包约 1.3 MB 量级，仍在 1.5 MB 红线内）。
