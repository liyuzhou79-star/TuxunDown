# TuxunDown v4.7.0

4.7.0 主要做三件事：把任务的登录状态（Cookie）的发送范围收紧到原站；让相邻的小分片合并成一次请求下载；扫码加链接和其它入口走同一道支持检查。没有承诺任何速度倍数，下面只讲具体改了什么。

## 安全

- **登录状态只发给原站**：有些下载要带上你在网站上的登录状态（Cookie）才能下，比如从网盘类站点、需要登录的论坛附件区抓下来的任务。这一版排查会话与入口相关的代码时发现：以前这份 Cookie 的发送不分站点——你为了加速粘了一个镜像地址，下载分片会去镜像站请求，那份原站的 Cookie 也会原样发给镜像站；服务器把下载跳转到另一个站点时也一样。镜像是你为速度选的，不该顺手把原站的登录状态也交出去。现在改成按站点隔离：Cookie 只在请求地址和任务链接是同一个站点时才发送，镜像和跳转不会再带上你在原站的登录状态；同站的正常跳转照常带，嗅探时在原站页面里抓到的登录状态也照常用于那个任务，需要原站会话的下载不受影响。顺带把其它入口逐项复查了一遍：分享进来的链接、导入的链接清单都走同一道清洗和支持检查；剪贴板只在 App 打开着的时候读一次、只取里面的第一个链接，原文不会存下来；备份、导出的任务清单、速度曲线、复制出去的诊断信息都不带 Cookie 和授权头——这些结论都写进了代码注释里。

## 优化

- **相邻的小分片合并成一次请求**：多线程下载会把文件切成很多小块分别下。切得细的区域（大文件开局的细分区、小文件均匀切分时）每块只有一两百 KB，以前每一小块都要单独发一次请求：一次往返、一次响应头，块越小、这类固定开销占比越高。现在一条连接领到一块时，会顺手把后面相邻的几块一起领走（有上限：每块不超过 1 MB、合并后总长不超过 2 MB、最多 4 块），用一次请求连续下完。适用场景就是上面说的细切分区——块本来就大的下载不受影响，也不需要你改任何设置。代价也如实说：如果一次合并下载中途失败，这一段要整段重下，但一段最多 2 MB，和以前单个分片下到一半失败要重下的量是同一量级；已经下好的分片进度一点不动，断点续传的记账方式没有变。

## 修复

- **扫码加链接补上同一道支持检查**：粘贴链接、分享链接进来时，都会先检查这个链接是不是 App 支持的类型（http / https / ftp / 迅雷链接等），不支持的当场说明。扫码这条入口之前漏了这一道：二维码内容虽然实际上只可能是网页链接或迅雷链接，但万一扫到内容异常的二维码，会建出一个下不了的任务、到下载时才报错。现在扫码解出的链接也先过同一道检查，不支持的当场用原来的提示说明，不再建任务。

## 说明

- 这一版还认真评估过一件事，结论是**不做**：上一版新增的「服务器画像」（峰值速度、峰值连接数、各下载源贡献）要不要反过来影响新任务的开局连接数。评估下来，开局连接数已经有专门的学习记录在管——每次下载完成后会记住这台服务器实测最合适的连接数，下次同站直接按它起步，这个数字是整个下载过程反复试探后留下的结论；而画像是单个任务的峰值展示数据，两个峰值还不一定出现在同一时刻，拿它反推开局连接数反而更不准。所以画像保持只做展示，决定和理由写在了相关代码的注释里。
- 升级方式不变：正式签名与之前一致，直接覆盖安装即可，不用卸载，任务记录都保留。
- 没有新增任何权限；没有新增任何第三方依赖。本版的 Cookie 站点判断和分片合并规则都是纯逻辑，带单元测试。
- 安装包体积：以正式发布包实测为准（仍在 1.5 MB 红线内）。
